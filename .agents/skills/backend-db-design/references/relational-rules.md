# Relational Design Rules

Read this while defining tables, keys, columns and constraints in Step 4. The general principles (3NF, constraints over convention, indexes follow queries) are in `<shared>/principles.md` -> Database. This file holds the concrete rules.

## Naming

- Tables: `snake_case`, plural (`order_items`). Columns: `snake_case`, singular.
- FK columns: `<referenced_table_singular>_id` (`user_id`).
- Constraints and indexes: `<table>_<columns>_<kind>`, e.g. `users_email_key`, `posts_user_id_idx`, `orders_status_check`.
- Match the project's existing convention when it differs. Live code wins over this list.

## Primary Keys

Pick one strategy per project and record it in `decisions.md`.

| Option | Use when | Notes |
|---|---|---|
| `BIGINT GENERATED ALWAYS AS IDENTITY` (PG) / `BIGINT AUTO_INCREMENT` (MySQL) | Internal tables, IDs never exposed, single database | Smallest and fastest. Do not expose sequential IDs in URLs if enumeration matters. |
| UUIDv7 | IDs are exposed, generated by clients or several services, or data is merged across databases | Time-ordered, so inserts stay index-friendly. PostgreSQL 18 has a built-in `uuidv7()`; on older versions generate UUIDv7 in the application. In MySQL store as `BINARY(16)`. |
| Identity PK plus a `public_id` UUIDv7 column | You want compact joins but opaque external IDs | Unique index on `public_id`; APIs use only `public_id`. |
| UUIDv4 (`gen_random_uuid()`) | Already the project convention | Works in PostgreSQL but random inserts fragment indexes; avoid as the clustered PK in MySQL. |

Tell `backend-migrate` the PK type: batched backfills page by key, and integer-range batching does not work on UUIDs.

## Columns

- Every column is `NOT NULL` unless absence is a real state. A column with a default is still `NOT NULL` unless null means something.
- Timestamps: PostgreSQL `timestamptz`; MySQL `DATETIME(6)` holding UTC with the session `time_zone` set to `+00:00`. Store UTC; convert at the edges. MySQL `TIMESTAMP` stops at 2038.
- `created_at NOT NULL DEFAULT now()`. `updated_at` needs a trigger (PostgreSQL) or `ON UPDATE CURRENT_TIMESTAMP(6)` (MySQL) or a single ORM hook; a default alone never changes after insert.
- Enumerations: a `CHECK (status IN (...))` constraint or a lookup table. Use a lookup table when values carry attributes or change often. PostgreSQL `ENUM` types are hard to remove values from.
- Text: `text` (PG) or `VARCHAR(n)` with a real business limit. Do not default every column to `VARCHAR(255)`.
- JSON (`jsonb`, MySQL `JSON`) only for data that is read and written as a whole and never filtered on heavily. Facts you query or join on get real columns.

## Case, Unicode and Collation

- Identifiers users type (email, username, slug) need case-insensitive uniqueness. PostgreSQL: a unique index on `lower(email)`, or the `citext` type. MySQL: the default `utf8mb4_0900_ai_ci` collation is case- and accent-insensitive; choose a collation deliberately.
- Normalize identifiers before storing them: Unicode NFKC plus case folding, in the application. Store the normalized form in its own column (`email_normalized`) when you also need the original.
- PostgreSQL: database encoding `UTF8`. Pick the collation (libc or ICU) on purpose; it affects sort order and index use.
- MySQL: `utf8mb4` everywhere, at database, table and connection level.

## Foreign Keys

- Declare every relationship as a FK. Skipping FKs "for speed" is a measured exception, recorded in `decisions.md`.
- PostgreSQL does not index referencing columns automatically. Index every FK column used in joins, or whose parent rows are deleted or have their key updated; otherwise each parent delete scans the child table. MySQL InnoDB creates the index for you.
- Choose `ON DELETE` per relationship:

| Behavior | Use when | Example |
|---|---|---|
| `RESTRICT` / `NO ACTION` (default) | The child has its own value or history | `orders.customer_id` |
| `CASCADE` | The child is part of the parent aggregate and meaningless without it | `order_items.order_id` |
| `SET NULL` | The link is optional and the child survives | `posts.category_id` (nullable) |

- Avoid `CASCADE` across aggregates or with large fan-out: one delete can lock and remove many rows. Prefer an explicit, batched application delete there.
- `ON UPDATE CASCADE` is rarely needed when keys are immutable. Keep keys immutable.

## Soft Delete and Data Retention

- Use one deletion mechanism. Either `deleted_at timestamptz NULL` or a status value, never both.
- Uniqueness must ignore deleted rows, or users cannot re-register: PostgreSQL partial unique index `WHERE deleted_at IS NULL`; MySQL generated column, see `schema-templates.md`.
- Default queries filter `deleted_at IS NULL`. Index for that filter where lists are hot.
- Soft-deleted rows still hold personal data. Define a retention period, then hard-delete or anonymize (null or hash the personal columns). Record the policy in `decisions.md`.

## Money

- Never `FLOAT` or `DOUBLE`.
- Either integer minor units (`amount_minor BIGINT`) or `NUMERIC(19,4)` / `DECIMAL(19,4)`. Pick one per project.
- Store the currency next to every amount: `currency CHAR(3)` (ISO 4217), `CHECK (currency ~ '^[A-Z]{3}$')` in PostgreSQL.
- Store exchange rates and the rate used on each conversion; never recompute history from today's rate.

## Concurrency Columns

Optimistic locking with a version column:

```sql
ALTER TABLE orders ADD COLUMN version integer NOT NULL DEFAULT 0;  -- new tables: declare it inline

UPDATE orders
SET status = $1, version = version + 1, updated_at = now()
WHERE id = $2 AND version = $3;
-- 0 rows updated = someone else changed it: reload and retry, or return a conflict
```

`backend-api-design` exposes this as ETag / If-Match (412) or 409. Use pessimistic `SELECT ... FOR UPDATE` only for short, hot critical sections such as inventory decrement.

## Sensitive Columns

- Classify columns: public, internal, personal data (PII), sensitive (government IDs, health, payment). Record the classification in the design.
- Store the minimum. Do not store card numbers; use the payment provider's token.
- Passwords: only a slow hash (argon2id, bcrypt, scrypt). `backend-auth` owns the credential tables.
- Highly sensitive fields: encrypt in the application with keys from a KMS or secret manager (envelope encryption). For lookups on an encrypted field, add a keyed hash column (blind index).
- Tokens (refresh, reset, API keys): store a hash, never the raw value.
- Never put secrets or personal data in index names, comments or seed data.

## Audit and Outbox Tables

- Audit: append-only `audit_log` (actor_id, action, entity_type, entity_id, before, after, occurred_at, request_id). Revoke UPDATE and DELETE on it from the app role. Exclude secrets and tokens from `before` and `after`.
- Events to other systems: an `outbox` table written in the same transaction as the business change. The relay, retries and idempotent consumers are owned by `backend-ops`.

## Transaction and Constraint Design

For each critical write flow, state:

1. Transaction boundary: which statements commit or fail together; which side effects (email, HTTP calls, events) run after commit via the outbox.
2. Concurrency strategy: unique constraint, optimistic version column, `SELECT ... FOR UPDATE`, or idempotency key.
3. Constraint split: local invariants in DB constraints (`CHECK`, `UNIQUE`, FK); rules spanning aggregates in application transactions.
4. Denormalization: what is duplicated or computed, why (measured need), and how it stays correct (trigger, same transaction, rebuild job).
