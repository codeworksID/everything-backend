# SQL and Query Safety

> **Single source of truth** for injection-proof data access. Every skill that writes, reviews, tests or fixes code that queries a database follows it: backend-implement, backend-refactor, backend-debug, backend-db-design, backend-api-design, backend-auth, backend-test, backend-doctor and backend-security. A skill may add stack detail but must not weaken these rules. Rule and step numbers are stable; other skills cite them.

Any query that can be reached from a public endpoint must be safe against **hostile input**. Treat every value as untrusted when it comes from: path params, query strings, request bodies, GraphQL variables, headers (including `Host`, `X-Forwarded-For`, `User-Agent`, `Referer`), cookies, token claims, uploaded file names and contents (CSV, XML), message queues, webhooks, third-party APIs, or **the database itself** (second-order injection, below).

**Out of scope here:** mass assignment (binding request fields onto a model), XSS, command injection, SSRF, deserialization and the rest of secure coding. They are covered by `secure-coding.md` (S1-S18), which applies alongside this file; this file is only about how queries are built and scoped. `scripts/security-scan.js` checks both.

## The Rules

1. **Values are always bound parameters.** Never put a value into SQL text by concatenation, `+`, template literals, f-strings, `%` formatting, `.format()`, `Sprintf`, `String.format` or string builders. Use placeholders (`$1`, `?`, `:name`, `%s` with a separate params tuple) and pass the values separately. This holds for internal admin endpoints, background jobs, migrations and stored procedure calls too. Never put quotes around a placeholder (`'%s'`, `'?'`): the driver quotes it.
2. **Identifiers come from an allowlist.** Table names, column names, sort fields, sort direction, JSON paths and SQL keywords cannot be bound as parameters. Map the client's value to a fixed server-side constant (`{"created": "created_at", "name": "last_name"}`), reject anything else with 400, and never pass the client's string through, not even "escaped". If a dynamic identifier is unavoidable, quote it with the database's identifier function (Postgres `format('%I', ...)` / `quote_ident`, psycopg `sql.Identifier`, `pgx.Identifier{...}.Sanitize()`, Drizzle `sql.identifier`, Knex `??`, T-SQL `QUOTENAME`), and still validate it against the allowlist first. Sorting on an arbitrary column is also a data oracle (sort by `password_hash` and watch the order), so the allowlist matters even when quoting is correct.
3. **A WHERE clause is not an access check.** `WHERE id = $1` with a client-supplied id is a correct query and an insecure endpoint. Every read and write of a tenant- or user-owned row also binds the owner from the authenticated principal: `WHERE id = $1 AND tenant_id = $2` (`$2` comes from the session or verified token, never from the request body, path, query or a header the client controls). Missing this is BOLA/IDOR (OWASP API1). See backend-auth -> tenant-scoped authorization. Postgres row-level security (`FORCE ROW LEVEL SECURITY`, app role not the table owner and without `BYPASSRLS`) is a good backstop, not a replacement.
   - **ORM trap:** an `undefined` value in a where object drops the condition. Prisma `findFirst({ where: { id: undefined } })` and TypeORM `findOne({ where: { id: undefined } })` return the first row of the table. Validate that every key and owner value is present and of the right type before the query runs.
4. **Writes are bounded.** UPDATE and DELETE always have a WHERE that includes the key and the owner. Check the affected row count and treat 0 as not found. Bulk operations take an explicit, validated, size-limited list of ids. Never build "WHERE 1=1" plus optional fragments from strings; use the query builder's conditional API or an array of fragments joined from fixed SQL with bound values.
5. **Lists use array binding.** Postgres: `WHERE id = ANY($1::bigint[])` with the array as one parameter (node-postgres, pgx, asyncpg and psycopg all send a native array). Elsewhere use the driver's list expansion: SQLAlchemy `column.in_(ids)` or `bindparam("ids", expanding=True)`, `sqlx.In` + `Rebind`, Dapper `IN @ids`, JPA `IN :ids`, Spring `NamedParameterJdbcTemplate` with a collection, MyBatis `<foreach>` over `#{}`. Never `",".join(ids)` into the SQL text. Cap the list length (Postgres allows 65535 bind parameters per statement, SQL Server 2100).
6. **LIKE patterns are escaped and bound.** Escape the escape character first, then `%` and `_` (SQL Server also `[`). Build the wrapped pattern in code and bind it whole: `name LIKE $1 ESCAPE '\'` with `$1 = "%" + escaped + "%"`. Portability notes: in MySQL a backslash inside a string literal is itself an escape, so write `ESCAPE '\\'` or pick another escape char (`ESCAPE '!'`, escaping `!` too); in MySQL `||` is OR unless `PIPES_AS_CONCAT`, so do not build `'%' || ? || '%'` there. Helpers: Rails `sanitize_sql_like`, SQLAlchemy `.contains(v, autoescape=True)`. A user-supplied regex (`~`, `REGEXP`, Mongo `$regex`) is a pattern too: escape it or reject it, and bound its length (ReDoS). Prefer full-text search or trigram indexes for search features.
7. **Raw-SQL escape hatches are banned for user input.** Each ORM has an "unsafe" or "raw" API (table below). Use the safe variant; if the unsafe one is truly needed, its arguments must be compile-time constants or allowlisted identifiers, with a comment saying so. Do not build an interpolated string in a variable and then pass the variable to a raw API: EF Core `FromSqlRaw(s)`, Prisma `$queryRawUnsafe(s)` and similar lose the binding that the inline tagged/interpolated form gives.
8. **Dynamic SQL inside the database is still SQL.** In PL/pgSQL use `EXECUTE format('SELECT ... FROM %I WHERE x = $1', ident) USING value` (`%I` for identifiers; prefer `USING` over `%L` for values). In T-SQL use `sp_executesql` with typed parameters and `QUOTENAME` for identifiers. In MySQL use `PREPARE ... FROM` with `EXECUTE ... USING @v`. Never `EXECUTE 'SELECT ... ' || value`. Calling a stored procedure with parameters is only safe if the procedure does not concatenate inside. Give `SECURITY DEFINER` functions a fixed `SET search_path = pg_catalog, pg_temp` (plus the needed schema, schema-qualified objects preferred).
9. **NoSQL has injection too.** In MongoDB, reject objects where a scalar is expected: a login body of `{"password": {"$ne": null}}`, or the query string `?password[$ne]=` parsed by `qs`/Express, bypasses auth. Strip or reject keys that start with `$` or contain `.`. Never use `$where`, `$function`, `$accumulator` or `mapReduce` with user input. In Mongoose, set `sanitizeFilter: true` (wraps nested `$` operators in `$eq`; use `mongoose.trusted()` for your own operators); note that `strictQuery` only drops paths not in the schema and does **not** stop operator injection on a real field such as `password`. In Redis, never build Lua scripts or command strings from input; pass keys via `KEYS` and values via `ARGV`. In Elasticsearch/OpenSearch, never put input into `query_string` or a script source; use `match`, `term` or `simple_query_string`, and pass script values as `params`.
10. **Validate at the boundary as defense in depth, not as the fix.** Schemas (Zod, Pydantic, Bean Validation, `binding:` tags) enforce type, length, format and enum values before the service layer. Type checks also stop object/array injection into drivers that expand them (mysql/mysql2 turn `{a: 1}` into `` `a` = 1 ``, so `WHERE password = ?` with an object can become always-true; set `stringifyObjects: true` or reject non-scalars). Validation never replaces parameterization.
11. **Least privilege limits the blast radius.** The application role has only the DML it needs on its own schema: no DDL, no `SUPERUSER`/`BYPASSRLS`, no table ownership, no `FILE` (MySQL), no `pg_read_server_files`/`pg_write_server_files`/`pg_execute_server_program`, no `xp_cmdshell` (SQL Server), no access to other tenants' schemas. Migrations run with a separate role. Keep multi-statement execution off: `multipleStatements: false` in mysql/mysql2 (the default); node-postgres and psycopg accept several statements only on unparameterized queries, which rule 1 already bans. Set `statement_timeout` (or the engine's equivalent) so a crafted expensive query can't hold connections.
12. **Errors don't leak SQL.** Map database errors to generic API errors; log the detail server-side without values. Never return driver messages, query text or stack traces to clients. Error text that differs between "row exists" and "row does not" is an oracle too.

## Second-Order Injection

Data that passed through the database is not trusted again on the way out. Example: a user registers with the display name `x' OR '1'='1`. The insert is parameterized and stores it safely. Later a nightly report job reads names and runs `` db.query(`SELECT * FROM orders WHERE customer_name = '${row.name}'`) ``, and the stored payload executes with the job's (often higher) privileges. The same applies to values from config tables, saved filters, saved report definitions, and column names stored as "user preferences". Rule 1 and rule 2 apply to every query, whatever the source of the value.

## Safe vs Unsafe APIs per Stack

| Stack | Safe | Unsafe with user input |
|---|---|---|
| node-postgres (`pg`) | `client.query('... WHERE id = $1', [id])`, `= ANY($1)` with an array, `pg-format` `%I` for allowlisted identifiers | template literal or `+` into the text |
| mysql2 | `execute('... WHERE id = ?', [id])` (server-side prepared), `query('... ?', [id])` (client-side escaped, safe for scalars) | `query(\`... ${id}\`)`; objects/arrays as values without type checks; `multipleStatements: true` |
| Prisma | `` $queryRaw`... ${id}` `` and `` $executeRaw`...` `` (tagged template binds), `Prisma.sql`, `Prisma.join`; client methods with validated where values | `$queryRawUnsafe`, `$executeRawUnsafe`, `Prisma.raw(input)`; `undefined` in a where (rule 3) |
| Drizzle | `` sql`... ${id}` ``, query builder (`eq`, `inArray`), `sql.identifier` for allowlisted names | `sql.raw(input)` |
| Knex | `.where('id', id)`, `knex.raw('... ?', [id])`, `whereRaw('x = ?', [v])`, `??` for allowlisted identifiers | `knex.raw(\`... ${v}\`)`, `whereRaw` / `orderByRaw` with interpolation; objects passed to `.where()` on MySQL (keep Knex >= 2.4) |
| Sequelize | `replacements` (escaped inline) or `bind` (real bind params) options, model finders | `sequelize.literal(input)`, interpolation in `sequelize.query`, `order` / `attributes` from input |
| TypeORM | `.where('u.id = :id', { id })`, `:...ids` for lists, `query(sql, [params])`, repository finders with validated values | interpolation in `.where()`, `.orderBy(input)`, `.select(input)`, `query()` with interpolation; `undefined` in a where (rule 3) |
| SQLAlchemy | Core/ORM expressions, `text('... :id').bindparams(id=v)` or `session.execute(text(...), {"id": v})`, `in_()` / expanding bindparam | `text(f"...")`, `literal_column(input)`, `.order_by(text(input))`, `.filter(text(f"..."))` |
| psycopg 2/3, asyncpg | `cur.execute('... %s', (v,))`, `sql.SQL(...).format(sql.Identifier(col))`; asyncpg `conn.fetch('... $1', v)` (asyncpg has no identifier quoting: allowlist) | `cur.execute(f"...")`, `'...' % v` or `.format()` into the text |
| Django | ORM, `.raw('... %s', [v])`, `cursor.execute(sql, [v])`, `RawSQL(sql, [v])`, `.extra(where=['x = %s'], params=[v])` | `.raw(f"...")`, `.extra(where=[f"..."])`, `RawSQL` with interpolation, `'%s'` quoted placeholders, `filter(**request.GET.dict())` / `order_by(input)` / `values(*input)` without an allowlist |
| Go `database/sql`, pgx, sqlx | `db.QueryContext(ctx, "... $1", v)` (`?` for MySQL), `sqlx.In` + `Rebind`, `pgx.Identifier{...}.Sanitize()` | `fmt.Sprintf` / `+` into the query (any verb, including `%d`); pgx simple protocol on old versions (keep pgx >= 5.5.4 / 4.18.2) |
| GORM | `Where("name = ?", v)`, struct/map conditions, `First(&u, "id = ?", id)`, `clause.OrderByColumn{Column: clause.Column{Name: allowlisted}}` | `Where(fmt.Sprintf(...))`, `First(&u, idString)` / `Find(&u, idString)` with a string id (treated as SQL), `Order(input)`, `Select(input)`, `Group(input)`, `Table(input)`, `Raw` / `Exec` with interpolation |
| JDBC / Spring | `PreparedStatement` with `setX`, `JdbcTemplate.query(sql, rowMapper, args...)`, `NamedParameterJdbcTemplate` | `Statement.execute(str + v)`, concatenation into `jdbcTemplate.query` / `prepareStatement` |
| JPA / Hibernate | JPQL/HQL with `:param` and `setParameter`, Criteria API, Spring Data derived queries and `@Query` with `:param` | concatenation into `createQuery` / `createNativeQuery`; `ORDER BY` from input; `JpaSort.unsafe(input)` |
| MyBatis | `#{value}`, `<foreach>` over `#{}` | `${value}` (string substitution; only for allowlisted identifiers) |
| .NET EF Core / Dapper | `FromSql($"... {v}")` (EF Core 7+), `FromSqlInterpolated`, `ExecuteSql` / `ExecuteSqlInterpolated`, `FromSqlRaw("... {0}", v)` with parameters, Dapper `new { v }` and `IN @ids` | `FromSqlRaw` / `ExecuteSqlRaw` with concatenation, `string.Format`, or a pre-built `$"..."` string |
| Rails ActiveRecord | `where(id: v)`, `where("x = ?", v)`, `where("x LIKE ?", "%#{sanitize_sql_like(v)}%")` | `where("x = #{v}")`, `order(params[:sort])`, `Arel.sql(input)`, `pluck` / `select` / `group` from input, `find_by_sql` with interpolation |
| Laravel / PDO | Eloquent, `where('x', $v)`, `DB::select('... ?', [$v])`, PDO `prepare` + `execute` (set `PDO::ATTR_EMULATE_PREPARES => false` on MySQL) | `DB::raw($input)`, `whereRaw("x = $v")`, `orderByRaw($input)`, column names from input (`orderBy($request->sort)`, `where($request->col, ...)`), `PDO::query` with concatenation |

The stack files in `stacks/` show full examples for Postgres, Node/TypeScript and Python/FastAPI.

## Verification (required before a change is reported as done)

1. **Static search.** Run `node <shared>/scripts/security-scan.js --changed` (rules `sql-*`, `mybatis-*`, `nosql-*`), then the "No SQL built from strings" check (backend-implement -> post-generation checklist, check 3) and the injection-sink table (backend-doctor -> static checks) over every changed file. Also search for the unsafe APIs in the table above. Read every hit in context; a hit is fixed or justified with `file:line`.
2. **Read every changed repository/DAO file.** Multi-line query building, helper functions that return SQL fragments and values read back from the database (second-order) escape line-based patterns.
3. **SAST when available.** `semgrep scan --config p/sql-injection --config p/<language> --metrics=off` (installing semgrep is Always Ask First). Bandit `B608` (string-built SQL), `B610` (Django `extra`) and `B611` (Django `RawSQL`) for Python; gosec `G201` (SQL format string) and `G202` (SQL string concatenation) for Go; Brakeman (SQL Injection warnings) for Rails; SpotBugs + Find Security Bugs (`SQL_INJECTION_*`) for Java; CodeQL `*/sql-injection` queries where CodeQL runs. A clean scan does not replace steps 1, 2 and 4.
4. **Negative tests.** For each endpoint that takes a search, filter, sort, id or free-text parameter, add tests (backend-test -> security tests) that send hostile input and assert the response is a 400 or an empty/own-tenant result, never extra rows, a 500, a changed row count, or a slower response:
   - values: `' OR '1'='1`, `1 OR 1=1`, `1; DROP TABLE users--`, `' UNION SELECT NULL--`, `'/**/OR/**/1=1#`, `\`, `%`, `_`, a 10 kB string, Unicode quotes (`ʼ`, `＇`), NUL bytes;
   - time-based: `'; SELECT pg_sleep(5)--`, `' AND SLEEP(5)--`, `'; WAITFOR DELAY '0:0:5'--` (assert the response time stays normal);
   - sort and field parameters: `id; DROP`, `name desc, (select 1)`, `password_hash`, an unknown column;
   - JSON bodies and query strings with operator objects: `{"email": {"$ne": null}}`, `{"id": {"$gt": ""}}`, `?email[$ne]=x`, arrays or objects where a scalar is expected, a missing id (`undefined` must not match the first row);
   - second-order: store a payload through one endpoint, then call every feature that reads it back (reports, exports, search, jobs);
   - another tenant's or user's id (must return 404 or 403, not the row).
5. **Exit criterion.** A change that builds SQL from strings with untrusted input, uses an unsafe raw API with input, or lacks an owner predicate on a tenant/user-owned row is **not done**. Severity when found in review: Critical when reachable from a public or low-privilege endpoint, High otherwise.
